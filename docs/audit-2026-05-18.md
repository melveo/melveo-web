## Findings

### P1 — `ImageGridScrollMorph` Performance Hotspot

**Status:** local optimization implemented, production decision pending visual approval
**Affected file:** `src/components/ImageGridScrollMorph.astro`

The morph section was the only major area that caused visible scroll jank in Chromium. The original isolation test at `1440x900` showed:

| Variant | Avg frame | P95 frame | Max frame |
|---|---:|---:|---:|
| Normal | 52 ms | 90 ms | 156 ms |
| `?morph=no-smoke` | 45 ms | 132 ms | 137 ms |
| `?morph=no-scroll` | 19 ms | 35 ms | 91 ms |
| `?morph=no-scroll,no-smoke` | 15 ms | 26 ms | 84 ms |

This points to the scroll-linked morph/reveal animation as the main source, not the decorative smoke layer.

Implemented local change:

- Removed Motion `scroll()` timelines from `ImageGridScrollMorph`.
- Replaced them with one passive `scroll` listener + `requestAnimationFrame`.
- The controller now writes only `transform`, opacity, `--reveal-progress`, and one debounced class swap for the clip-path transition.
- Surrounding honeycomb reveal now starts later, after the main photo is mostly finished shrinking, reducing overdraw during the expensive part.

Local re-test after restart:

| Viewport | Avg frame | P95 frame | Max frame |
|---|---:|---:|---:|
| 390×844 | 17 ms | 37 ms | 47 ms |
| 768×1024 | 22 ms | 49 ms | 80 ms |
| 1440×900 | 28 ms | 108 ms | 132 ms |
| 1920×1080 | 32 ms | 114 ms | 137 ms |

Mobile/tablet improved clearly. Desktop still has occasional long frames because the section is visually heavy and uses many clipped image hexagons, but the persistent Motion scroll machinery is removed.

**Next recommendation before production:**

1. Manually approve the visual rhythm on localhost.
2. If desktop Chrome still feels heavy, optimize image delivery next: smaller thumbnails for honeycomb cells and one high-quality image only for the opening full-screen photo.
3. Keep `prefers-reduced-motion` as a static honeycomb layout.

### P1 — Oversized Honeycomb Images

**Status:** needs improvement
**Affected file:** `src/components/ImageGridScrollMorph.astro`

Lighthouse reports roughly **1.0 MB image delivery savings** on mobile preview. Several honeycomb photos are loaded at large source dimensions while displayed as small hex cells.

**Recommendation:**

Use responsive image variants:

- Keep one high-quality image for the initial large morph photo.
- Generate smaller WebP/AVIF variants for honeycomb cells.
- Prefer Astro `astro:assets` / responsive `srcset` where practical.
- Add explicit image dimensions for layout stability.

### P2 — Motion Console Warning

**Status:** investigate with the scroll refactor

The browser reported one Motion warning about scroll offset container positioning. It did not break the page, but it is another signal that the morph scroll setup should be simplified and made more deterministic.

**Recommendation:**

Resolve this as part of the `ImageGridScrollMorph` scroll-controller refactor.

### P2 — `mdn-data` Appears Unused

**Status:** cleanup candidate
**Affected file:** `package.json`

`rg` only finds `mdn-data` in `package.json`. If no generated tooling relies on it, remove it to reduce dependency surface.

### P2 — Performance Budget Should Be Automated

**Status:** missing process guard

The page can regress visually/performance-wise because the heaviest sections rely on scroll and canvas effects.

**Recommendation:**

Add a small CI check:

- `bun run check`
- `bun run build`
- `bun audit --audit-level low`
- Lighthouse CI on `/cs/` and `/en/`
- A Playwright smoke pass at key breakpoints: `390x844`, `768x1024`, `1440x900`, `1920x1080`
